# APPROACH — Aminobots Chat Triage Agent

> For Aminobots partner-support teams and reviewers. Architecture: [diagram](docs/architecture.drawio.svg); workflow: [diagram](docs/workflow.drawio.svg). Contracts and full evaluation details: [SPEC](docs/SPEC.md) and [ARTEFACT](ARTEFACT.md).

The deployed demo is [live on Render](https://aminobots-chat-triage-agent.onrender.com). It uses synthetic chats and simulates every action.

## A. Problem scoping

Partner-support staff need to find real requests buried in Telugu-English WhatsApp group exports, identify who asked, and decide what the assistant may do. Senior support handles approvals; finance handles payout changes; security reviews refusals. Exports include noise, split and on-behalf requests, forwards, ambiguous identities and unknown numbers.

The system parses Android `.txt` exports, extracts requests and evidence IDs, resolves sender identity against a roster, and grades each request under numbered rules. It records simulated actions and exposes a step-by-step web view. Hindi, iOS exports, media interpretation, long-chat chunking, replying to groups and real execution are deferred.

We measure request precision/recall/F1, attribution and identity state, grade and rule accuracy, over-autonomy, evidence validity, phantom acts, approval load, latency and cost. The pass rule is five hard gates and three targets, documented in [SPEC §12](docs/SPEC.md#12-evaluation); results are in [ARTEFACT §e](ARTEFACT.md#e-evaluation-results).

## B. System design

The pipeline parses the export, renders anonymised sender handles, asks one free model call per chat to describe requests, grounds evidence IDs, resolves identity in code, evaluates all policy rules, then appends one simulated JSONL record per request. The model returns extraction fields and uncertainty flags only; plain code decides identity, authority, grade and rule. It uses a fixed pipeline because deterministic, auditable policy decisions matter more here than open-ended tool use. A ReAct loop was rejected because free-form model decisions would be harder to audit and more exposed to chat text steering the decision.

A person approves or rejects `seek_approval` items; hand-offs go to the appropriate team and refusals raise security alerts. These remain simulated. Parse, model, network or schema failures mark the whole run `UNPROCESSED` and hand it off; unknown evidence is rejected, unresolved references require approval, and unmatched cases go to R10. The [workflow diagram](docs/workflow.drawio.svg) shows the failure path.

## C. Data and knowledge

All data is synthetic, fictional and CC BY 4.0. The 15-chat dev set was written by Claude Code from the [Phase 3 prompt](docs/build-prompts/phase-03-data.md); its Telugu is not native-reviewed. Two challenge chats were generated by Claude Code from the mandated scenarios and are not independent. The separate held-out set has 8 chats and 11 requests, authored by Ch Pranav, drafted with Claude (not the build agent), and Telugu-reviewed by Ch Pranav. It was not used for development or prompt tuning; its t06 gold was corrected after the first run identified a missed status query. See [data notes](docs/data/README.md) and [ARTEFACT §c](ARTEFACT.md#c-data-provenance).

The roster (`data/world/roster.yaml`) represents contacts, roles, outlets, shared phones and delegates. The policy (`policy/policy_v2.yaml`) represents risk, allowed roles and numbered rules. Code reads both directly; no retrieval index is needed. Frozen-data hooks and a pre-commit guard protect evaluation splits.

## D. Evaluation framework

Evaluation matches requests by intent and evidence overlap (Jaccard ≥ 0.5), with Hungarian assignment. Metrics include detection precision/recall/F1, attribution, unconfirmed-sender recall, grade confusion, over-autonomy (including high-risk), rule citation, evidence validity and approval load. Hard cases include unknown senders requesting account data, payout changes, complaints, refunds and extraction failures. Five hard gates cover high-risk over-autonomy, unconfirmed-sender recall, evidence validity, phantom acts and exact mandated-scenario outcomes; targets are F1 ≥ 0.85, grade accuracy ≥ 0.85 and rule accuracy ≥ 0.90.

The v1.2-tagged held-out runs are recorded as [v1.1-test](eval/results/v1.1-test/report.md) and [v1.1-test-r1](eval/results/v1.1-test-r1/report.md). The corrected-gold r1 run scored F1 1.00, grade accuracy 1.00, rule accuracy 0.91 and zero phantom acts; it used cached model responses. Latency was 23.67s p50 and 35.60s p95. The first run used the original 10-request gold and exposed the missed t06 query; report both runs and the correction transparently. The 8-chat set is small, the dev scores are fitted, and the challenge set was builder-generated and seen. There is no baseline.

## E. Risks and responsibility

A wrong `act` on payout details could cause financial harm; R1 always hands payout changes to finance and R2 refuses risky or account-data requests from unconfirmed senders. Wrong attribution can grant authority to the wrong person, so identity comes only from the roster. Missed requests delay service; failed runs hand off instead of appearing empty. Excessive caution increases approval work, measured as approval load.

The route layer only appends `simulated: true` JSONL rows. Approve/reject in the website writes to browser storage. A test checks that routing imports no network client. Phone numbers are masked before model input. Free-model providers may log prompts, so real partner chats must not be used. The deliberate trade-off is caution: uncertainty sends work to a person, costing time to reduce unsafe actions. The deployed [Results view](https://aminobots-chat-triage-agent.onrender.com/#results) shows evaluation and latency/cost measures; the demo may sleep while idle.

Read the whole group. Stamp only what’s real.

Partner WhatsApp groups bury a few real requests, and now and then a fake bank-detail change, under dozens of good-mornings.

The Triage Desk pulls out each request, checks the sender against the roster and stamps what may happen next. It executes nothing.

How it works

  1. The model describes. A free LLM reads the chat and lists each request: what is asked, which messages show it, what a follow-up refers to.
  2. Code decides who. The sender is looked up by phone in the roster. Claims and vouching in the chat never count.
  3. Code decides what. Ten written rules are all checked; the most cautious match wins, and the action is only logged.

      What these numbers do not show

      • The 15 dev chats were written by the same session that wrote the prompt, so these scores are optimistic and say little about new chats.
      • There is no baseline: nothing measures how much code-side grading beats one prompt that also grades.
      • The two challenge chats (the mandated scenarios) were generated by the same agent that built the system, so they are not an independent test. Scenario 2 passes exactly; scenario 1 fails: both slot changes went to approval (R6) and a noise message was stamped “act”.
      • The free model leaves slot day and time empty, so open slot changes fall back to “ask approval” (R6) and the 12-hour rule (R7) cannot decide.
      • Rule-citation accuracy misses its 0.90 target.
